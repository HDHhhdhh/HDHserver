결론
rename, move, delete, upload 모두에서 filesystem 변경 직후, material journal 생성 전 os._exit(86)를 주입하면 파일만 바뀌고 세 JSON은 원래 바이트인 불일치를 재현했다.
수정 후 동일 지점은 파일을 원상복구한다. durable committing marker 이후의 종료는 filesystem을 유지하고 세 JSON을 목표 상태로 완료한다.
기존 pre-commit 동기 실패 rollback / metadata commit 이후 roll-forward 의미를 유지했다. 새 운영 정책 선택이 필요한 분기는 없었다.

이 작업에서 변경한 파일 (총 6개)
1. routes/api_fs.py
   - rename/move/delete/upload가 파일 변경 전 복구 intent를 기록한다.
   - move/delete는 같은 filesystem의 원자 rename을 사용한다. copy/delete fallback은 사용하지 않는다.
   - 업로드는 private staging에서 저장·fsync한 성공 파일만 publish한다. 부분 업로드 실패는 실제 files/와 DIR 배정에 남지 않는다.
   - delete/upload의 per-item 오류 응답을 유지한다. 중복/하위 delete 대상은 같은 inode를 한 번만 staging한다.
   - pre-commit rollback을 락 안에서 수행하며, committed 오류에는 파일을 복구하지 않는다.
   - tree GET도 shared journal을 복구한 뒤 조회한다.
2. core/material_state.py
   - material_state_lock이 file-tree → 결정적으로 정렬된 세 store 락을 함께 소유한다.
   - 기존 version 1 metadata journal / version 1 last-good snapshot을 계속 읽는다.
   - 파일 거래는 같은 material_state_transaction.json의 version 2, prepared/committing phase로 기록한다.
   - prepared는 원래 파일로 rollback하며 주 JSON 바이트를 다시 저장하지 않는다.
   - committing은 세 store를 roll-forward하고 private staging을 정리한 뒤 journal을 지운다.
   - intent 기록 후 primary store가 손상되어도 commit 직전 strict read가 거부하여 damaged bytes와 원래 파일을 보존한다.
   - 읽기/저장/복구의 optional files_dir 인자를 제공하되 기본은 materials_path.parent/files이다.
3. core/file_material_transaction.py (새 소형 모듈)
   - Flask/core.paths import 없이 injected root/store 경로의 filesystem plan을 검증한다.
   - store/root binding, segment 안전 경로, subtree 중복, device/inode/type identity를 검증한다.
   - 교체된 파일, source/target 동시 존재, 누락 등의 모호한 상태에서 덮어쓰지 않고 fail closed한다.
   - staging은 files root의 parent/instance/.file-delete-stage-<id> 또는 .file-upload-stage-<id>에 둔다.
     기존 ignored instance namespace를 사용하며 새 runtime JSON filename이나 .gitignore 변경이 없다.
4. scripts/verify_file_transaction_crash.py (새 전용 검증)
5. scripts/verify_file_transaction_routes.py (새 전용 검증)
6. docs/SERVER_FILE_TRANSACTION_FOLLOWUP_2026-10-01.txt (이 보고)

한계/운영 상태
- 검증은 프로세스 crash/restart를 다룬다. 전원 손실과 volume corruption에 대한 hardware durability 보증은 아니다.
- inode identity가 불안정한 filesystem, manual replacement, 잘못된 journal/path binding은 자동 복구 대신 관련 쓰기를 차단한다.
- core.storage의 기존 30초 stale lease grace/15초 acquisition timeout은 그대로다. 실제 abrupt exit 직후에는 grace 동안 read degraded/write unavailable일 수 있다.
- 이미 journal 없이 발생한 과거 rename/move/orphan staging 불일치를 이 패치가 소급 추정하여 수리하지 않는다. live repair는 별도 진단/승인된 maintenance/backup 대상이다.
- source와 parent/instance staging 사이 rename이 같은 filesystem이어야 한다. cross-volume copy/delete를 조용히 시도하지 않으며 실패 시 prepared rollback/fail closed한다.
- 운영 8003/8004 lifecycle, runtime data/DB/files, auth, commit/stage/push를 수행하지 않았다. 이 thread의 출력/쓰기 대상은 위 source/report, OS Temp synthetic fixtures/source baseline과 Python cache뿐이다.
- 하위 에이전트는 사용하지 않았다.
