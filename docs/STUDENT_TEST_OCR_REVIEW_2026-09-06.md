# OCR 기능·학습 세션 전면 검토: 2026-09-06

## 판단

기존 구현과 학습 자산은 보존할 가치가 있다. 그러나 지금은 **학습 체크포인트가 있는 연구 단계**이지 학생에게 자동 채점을 제공할 준비가 끝난 단계가 아니다. 세션의 가장 큰 문제는 학습량보다도 잘못 연결한 평가 입력, 서로 다른 지표의 혼용, 파일 설치와 운영 검증을 혼동한 완료 보고였다.

이번 작업은 평가·학습·출시 허용 경계를 분리하고 비동기 완료/실패 처리를 보강했다. 새 v4 실제 촬영이 없는 상태를 명시하며, 공공 데이터 기반 추가 GPU 실험과 실제 촬영을 요구하는 출시 검증을 분리한다. 이후 현재 상태의 정본은 [공개 데이터·학습 운영 메모](STUDENT_TEST_OCR_PUBLIC_DATA.md)다.

운영 8003 재시작, 운영 SQLite migration, 기능 활성화, 모델 파일 교체, 학습 데이터 삭제는 수행하지 않았다. 기존 unrelated dirty 작업도 보존했다.

## 유지한 사용자 결정

- 객관식은 버블을 읽는 기능이 아니라 **손으로 쓴 1~5**를 인식한다.
- 서버 카탈로그의 문항별 `answerModes`로 라우팅한다. 주관식 답이 `3`이어도 주관식 경로다. 시험 정답키를 OCR worker에 보내지 않는다.
- 공통수학1·2는 중3+고1, 대수·미적분1·확통·기하·미적분2는 중3+고1+고2+고3 프로필을 사용한다. 학생 현재 학년은 라우팅 기준이 아니다.
- 실시간 촬영, 0개 불확실 자동 채점, 1~3개 보완, 4개 이상 전체 재촬영을 유지한다. 주관식 두 차례 재촬영 후 보류, 관리자 당일 판정, 답지 정상 제공도 유지한다.
- 매 제출마다 교사 확인을 요구하는 운영으로 바꾸지 않는다. 최종 품질 표본의 독립 전사 확인은 일상 채점 절차와 다른 출시 검증이다.

### 이번 측정의 의미

`generated/ocr_review_20260906/inputs.json`은 원래 6개 case의 crop/전사와 v3 template 해시를 고정한다. benchmark v2는 명시된 경로에 따라 주관식 `1~5`도 평가한다. 이 때문에 기존 28문항과 새 60문항은 분모가 다르다.

| 경로·후보 | 숫자값/선지 일치 | 자동 수락 | 오수락 | 해석 |
|---|---:|---:|---:|---|
| 공용 숫자 v4 AI Hub 후보 | 27/38 (71.05%) | 18/38 (47.37%) | 0 | reject는 1/2; 운영 기본 v3를 교체하지 않음 |
| 수식 `m3_h1` | 21/60 (35.00%) | 0/60 | 0 | 진단용, 운영 검증 아님 |
| 수식 `m3_h1_h2_h3` | 24/60 (40.00%) | 0/60 | 0 | 진단용, 운영 검증 아님 |

결과 파일은 `generated/ocr_review_20260906/m3_h1.json`과 `m3_h1_h2_h3.json`이다. 두 실행의 입력 manifest SHA-256은 `219c66216462cf1f7edb8b1d2e385b9428e90b51a13effbf48af5c6fe88feb26`으로 같다. 새 수식 표본은 숫자 56개, 분수 1개, 루트 3개로 수식 다양성이 매우 부족하다. high-confidence 사람 전사 중 숫자 문법 밖의 항목도 별도 목록으로 남긴다. `rawAccuracy`는 숫자값 동치율이며 `transcriptionExact`는 정규화한 표현 일치다. 후자는 하위 20/60, 상위 23/60으로 숫자값 동치와 분리한다.

이 실행은 구형 v3 crop에 대한 진단이고, 과목별 실제 시험 라우팅이나 v4 전체 촬영 성능을 측정하지 않는다. 같은 진단 사진을 두 프로필에 넣었다고 두 개의 독립 시험이 되는 것도 아니다. `seconds`는 해당 UniMERNet crop 추론 구간이며 모델 로딩·보조 엔진·전체 촬영·대기열을 모두 포함한 p90가 아니다. 보조 worker timeout도 진단용 600초여서 실제 서비스 timeout과 다르다.

원본/보정본의 결과 합의는 첫 모델 60/60이었다. 이 합의는 별개 모델의 독립 증거가 아니며, 이미 흑백 이진화된 crop에서 autocontrast가 같은 입력을 만들 수 있다. 수락 0건에서 오수락 0건은 안전한 자동 채점이 입증됐다는 뜻이 아니다.

전처리 결과를 직접 열어 보니 q7 루트 위쪽 점선, person_02 q5 분수 주변의 가로/세로 답안칸 선이 남았다. **테두리 잔존은 관측**, 이것이 전체 오인식 중 얼마를 설명하는지는 **아직 미측정 가설**이다. 분수선·루트선을 보존하는 ablation 없이 일괄 선 제거를 운영 기본값으로 넣지 않았다.

## 미완료 운영 항목

다음은 문서에만 완료로 표시하지 않고 rollout 전 작업으로 남긴다.

1. **7일 자동 삭제 정기 실행:** `purge_expired_assets`와 관련 테스트는 있으나 실제 정기 호출이 없다. 인식 임시 파일 즉시 정리는 일부 개선일 뿐 7일 삭제 운영 완료가 아니다. 삭제 작업 실패 감지, orphan/부분 생성 폴더 정리 정책까지 검증해야 한다.
2. **작업 수명:** 현재 단일 프로세스 ThreadPool이다. 재시작 시 작업 회수, lease 만료/중복 worker, queue 누적, 채점 callback 실패 후 재시도, 완료 직전 새 작업 도착의 처리를 장애 주입으로 검증해야 한다. 이번 callback은 정상 완료 경로를 고친 것이지 durable scheduler 도입이 아니다.
3. **속도:** 큰 수식 모델과 보조 엔진을 매 subprocess에서 로드한다. warm worker, 입력 동일 variant 생략, 짧은 답안용 생성 상한 후보를 각각 정확도와 함께 비교해야 한다. 현재 p90 30초 충족 증거는 없다.
4. **당일 보류 처리:** 당일 확정은 관리자 운영 목표다. 보류 알림/일별 마감 점검과 실패 감지는 아직 운영 확인되지 않았다. 자정 자동 정답 판정으로 바꾸지 않는다.
5. **실제 v4 E2E:** 새 손글씨 사진이 없으므로 촬영→보정→인식→보완→저장 전 흐름의 실제 오류율·재촬영률·개인별 편차는 미검증이다. 기존 synthetic/VM/unit 통과와 구별한다.

## 추가 GPU 학습 계획

지금 당장 학생에게 새 라벨을 대량 작성하게 할 필요는 없다. 다음 순서로 한 요인씩 바꾼다.

1. 기존 상위 best4000을 회수하고 base/현재 반환/best의 동일 입력 비교를 고정한다.
2. 이미 가진 공식 Training으로 전체 수식 유지군과 짧은 숫자·분수·루트 중심 후보군을 만든다. Validation은 Training 작성자 제외 및 학년/표현 종류별 분리 결과를 함께 기록한다. 기존 전체 데이터는 삭제하지 않는다.
3. 동일 평가 입력에서 전처리 변경을 먼저 비교해 데이터/모델 문제와 분리한다. 실패 crop을 선택적으로 고쳐 놓고 전체 정확도 상승이라고 보고하지 않는다.
4. 학습량 실험은 dataset exposures와 optimizer updates를 따로 기록한다. 로컬 upstream `base_task.py`의 loop 기준, batch4·accum2·5,000 iteration은 명목 20,000 sample exposures와 약 2,500 optimizer update이며 40,000개의 독립 이미지를 학습한 뜻이 아니다. 다음 GPU에서 실제 sampler/로그로 재확인한다.
5. 후보 모델을 고른 뒤 calibration용 새 작성자와 최종 평가용 새 작성자를 분리해 v4 실카메라 데이터를 수집한다. 그때만 사용자 촬영 작업이 필요하다.

더 오래 학습하면 반드시 좋아진다는 보장은 없지만, 현재 결과만으로 추가 GPU 학습의 가치가 없다고 결론 내릴 근거도 없다. 작고 통제된 비교 실험으로 판단한다.

## 평가 주장 교정 근거

- **확인/교정:** 신경망 confidence가 실제 정답 확률과 자동으로 같아지는 것은 아니다. 그래서 현 token score 0.995를 99.5% 답안 정확도로 설명하지 않는다. [Guo 외, ICML 2017](https://proceedings.mlr.press/v70/guo17a.html).
- **확인/교정:** 동일 그룹이 train/test에 걸치지 않는 분할이 필요하다. 여기서는 작성자와 그 사진 변형을 그룹으로 취급한다. [scikit-learn 그룹 교차검증 문서](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data).
- **계산/한계:** `1 - 0.05^(1/299) <= 0.01`은 독립 이항 모형의 계산이다. 사진/crop 개수를 작성자 독립 표본 수로 치환하지 않는다. “26명이면 충분”, “299 crop이면 출시 가능”은 확정 기준이 아니다.
- **미검증 가설:** 테두리 제거, 목표 답안 중심 학습, 생성 상한 축소가 이 데이터에서 얼마나 개선하는지는 ablation 후 판단한다. 이 문서는 예상 개선율을 만들지 않는다.

## 검증 범위

`mandela`로 평가 입력/정답 유입/지표 한계를 감사했고, `ssotize`로 중복된 오래된 OCR 상태를 정본 링크로 정리했다. `sip`의 변경분 검증과 `factchk`의 confidence/group split 주장 확인을 적용했다. 동시 에이전트 슬롯은 메인 1개뿐이므로 별도 Astra 하위 에이전트의 독립 리뷰를 수행했다고 주장하지 않는다.

최종 전체 `scripts/verify_refactor_safety.py`는 exit 0으로 통과했다. OCR 관련 집중 회귀도 통과했다. 주요 확인은 config/readiness 39개, engine 28개, job runner 18개, service 34개, 로컬 정확도 계약 19개, formula training config 6개, profile training 14개, AI Hub 수식 변환/선별 20개다. 전체 suite의 오류 로그 중 synthetic failure 문구는 실패 주입 테스트이며 최종 실패가 아니다.

frontend 수정은 없으므로 새 browser QA는 수행하지 않았다. live app import/운영 smoke, 운영 데이터 보정, schema 적용, GPU 학습을 이 검증에 섞지 않았다. 실제 두 모델 추론은 CPU로 별도 실행하여 모두 NO_GO 진단 보고서를 저장했다. 기존 수식 데이터와 모델 weight는 그대로 유지했다. CUDA 재실행, 실제 카메라 출시 검증 및 앞 절의 운영 미완료 항목은 통과로 처리하지 않았다.
