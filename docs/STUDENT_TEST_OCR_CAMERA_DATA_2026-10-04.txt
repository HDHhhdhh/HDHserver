수집·검토 흐름
  이용 승인 → 가명·작성 안내 → 같은 종이 2회 촬영 → 원본에 연결된 20 crop
  → 안내/모델/정답키를 보지 않은 실제 전사 → 검증 snapshot/freeze
  → split별 추론 → 저장 JSONL 검토 → 나중에 별도 출시 holdout

수집 담당자가 할 일
1. 키트 안내를 읽고 이용 승인·비식별화·보관 정책의 reference를 확인한다.
   운영 촬영의 7일 삭제 승인은 수집자료의 장기 학습 재사용 허가를 대신하지 않는다.
2. W001~W024의 실제 학생 학년과 시험 과목을 확인한다. 기본 배정은 초기 진단 제안이다.
   과목은 서버의 curriculum 명칭을 쓴다. 학생 학년으로 OCR 프로필을 고르지 않는다.
3. 학생에게 해당 작성 안내만 보여 준다. 이름/SID는 답안지에 적지 않는다.
   한 종이에 작성한 후 흔들림 없이 두 번 촬영한다. 두 촬영 사이 답안을 고치지 않는다.
4. 사진을 모아 제공한다. 한 사진 복사나 필터 변형을 두 촬영으로 제출하지 않는다.
   담당자가 crop/metadata/SHA를 정리한다. 사용자가 960개 JSON 행을 먼저 채울 필요는 없다.
5. 독립 전사자는 crop만 보고 읽는다. 실제로 3 대신 8을 썼다면 8을 기록한다.
   작성 안내 값·시험 정답키·OCR 출력을 전사에 복사하지 않는다.
   빈칸/모호/지원 외 문항도 남긴다. 이 사람 검토는 개발 데이터 라벨용이며 매 제출 교사 확인 정책이 아니다.

개발·calibration/출시 경계
- global writerId는 같은 사람에게 항상 같다. 학년·과목별 새 ID로 분리하지 않는다.
- 동일 작성자·종이·두 사진·파생 crop·증강은 하나의 split에 둔다.
- 초기 계획은 development 16명/calibration 8명이다. calibration은 학습에 넣지 않는다.
- 24명×20칸×2사진은 960 photo-slot이지만 독립 작성자는 24명, 종이의 실제 필기는 480칸이다.
- 따라서 쓰는 개발용 자료는 자연스러운 시험 촬영의 대표성을 입증하지 못한다.
- 최종 release holdout은 새 작성자의 자연 필체로 별도 수집한다. 초기 freeze는 release export를 거부한다.
- 이름 가명화/동의/독립 전사는 담당자의 확인 기록이다. 이 도구가 신원·법적 권한을 독립 검증하지 않는다.
- SHA와 변환 receipt는 바이트 연결 증거다. 올바른 문항 영역을 잘랐다는 기하학적 증명을 대신하지 않는다.

실제 자료가 준비됐을 때의 명령 (프로젝트 루트에서)
  python -B -m scripts.student_test_camera_dataset freeze --intake <실제 INTAKE.json> --output <존재하지 않는 새 폴더>
출력은 FROZEN_LABELS.json, MODEL_INPUTS.json, 검증된 snapshot 사본이다.
전사 파일은 평가자에게만, MODEL_INPUTS는 추론자에게만 제공한다. 안내 txt를 추론자에게 주지 않는다.
snapshot은 OS 수준의 쓰기금지 저장소가 아니다. 추론 전/후 입력 SHA를 다시 확인해야 한다.
freeze의 해시/시각은 라벨 변경 여부를 추적한다. 사람이 실제로 독립 전사했다는 사실을 인증하지 않는다.

저장된 예측을 검토할 때 (새 OCR 추론을 시작하지 않는 명령)
  python -B -m scripts.student_test_camera_dataset score-saved --frozen <FROZEN_LABELS.json> --predictions <predictions.jsonl> --run <RUN.json> --output <새 결과 폴더>
- RUN schema: student_test_camera_prediction_run_v1. split과 frozenLabelsSha256, aware executedAt을 기록한다.
- modelBindings의 실제 route마다 checkpoint/architecture/tokenizer SHA를 기록한다.
  route는 choice_number 또는 m3_h1/m3_h1_h2_h3이다. 숫자 분류기의 tokenizer는 클래스 매핑 파일 해시다.
- 각 예측은 sampleId, cropSha256, text, autoAccepted(bool), modelRoute, modelSha256을 포함한다.
  수식 예측에는 tokenCount(int), eosSeen(bool)가 필요하다. 이는 보고된 metadata이지 토큰 ID 재관측이 아니다.
- inferenceCodeSha256과 acceptancePolicySha256, providerCallCount:0, deploymentReady:false를 기록한다.
- 선택 split의 모든 20칸/사진을 한 번씩 포함한다. 누락/중복/다른 crop·모델 바인딩은 거부한다.
  freeze 시의 scorer/정규화/과목 라우팅 코드 변경도 거부한다. 모델·추론·수락 정책 SHA는 보고된 실행 근거다.
- 숫자값 동치, 정규화 문자열 일치, 전체 숫자 실패, 생성 실패를 구분한다.
  미종료 또는 64 token 도달은 EOS가 있어도 생성 실패다. 실패를 분모에서 빼지 않는다.
- coverage는 전체 중 자동 수락 비율이다. falseAccepted는 자동 수락했지만 실제 전사와 다른 문항이다.
  blank/ambiguous/unsupported를 수락해도 falseAccepted다. 생성 실패와 숫자 실패는 단순 합산하지 않는다.
- 첫 촬영의 4개 이상 불확실/1~3개 보완만 집계한다. 두 재촬영 뒤 보류율은 실제 보완 기록 없이는 계산하지 않는다.
- latency는 사진마다 측정 범위를 붙인다. crop_inference_only를 photo_to_saved_grade 속도로 부르지 않는다.
  작은 두 사진 진단의 p90을 독립 출시 성능으로 주장하지 않는다.

GPU 비교 전 남은 준비
1. 촬영 증강의 필기 가독성을 검토한다. 약한 변형도 라벨 보존을 자동 보장하지 않는다.
2. 두 arm의 동일 초기 checkpoint·architecture/tokenizer·seed·batch4/accum2·학습 budget·LR/optimizer를 고정한다.
   현재 생성된 receipt의 trainingAllowed:false를 운영 플래그나 실행 승인으로 해석하지 않는다.
3. 같은 focused pool에서 증강 OFF/ON만 비교한다. 데이터 확대·모델 교체·수락 정책 변경은 별도 실험이다.
4. 공개 개발 validation과 촬영 development에서 동일 고정 분모를 사용한다. calibration으로 수락 정책을 정한다.
5. numeric strict 증가, text 및 모든 학년/작성자 numeric+text 비감소, 생성 실패 비증가 조건을 적용한다.
   single-seed 결과는 방향 진단이다. 이후 재현 seed를 늘리되 출시 holdout으로 학습/모델 선택하지 않는다.
6. NVIDIA 장치에서 별도로 실행한다. 학습/추론 승인·파일 전달·현재 초기 weight 선택은 별도 실행 경계다.
   현재 도구는 학습 실행 명령을 자동 호출하지 않는다. 증강 준비기는 고정 공개 Training SHA만 허용한다.
   public Test/학생 calibration/출시 holdout을 Training 입력으로 대체하지 않는다.

독립성 점검 (mandela)
- Recall, not reason / Shared hallucination: 작성 안내 값이나 모델 출력을 실제 필기 전사로 쓰면 순환 검증이다.
  전사 분리·blind 확인·pre-run freeze를 구현했다. 사람 확인의 독립성은 별도 확인 기록이 필요하다.
- Shared-pool bias: 같은 작성자·종이의 두 촬영을 다른 split에 넣거나 사진 수를 독립 표본 수로 세면 누출이다.
  global writer split/동일 종이 검사/정확 SHA 교차 검사로 막는다. 신원/near-duplicate 독립성까지 증명하지 않는다.
- Demand characteristics: 알려 준 20개 값을 특별히 정서하면 실제 시험 필체보다 유리할 수 있다.
  초기 진단으로만 사용하고 새로운 자연 필체 출시 holdout을 요구한다.
- 자체 #3~#5 점검: 임시 고정 fixture는 프로그램 계약 검사다. 외부 실제 필기 정답도 OCR 정확도 증거도 아니다.
  독립 하위 에이전트가 시간대/release 공개/crop 변경/template 사본 변경을 재현했고 수정 후 검사했다.
